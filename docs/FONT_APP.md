# フォントを別のアプリにする

**方針を決めた段階**。詳細（下の「詰めること」）はこれから決める。

## なぜ分けるか

[MODES.md](MODES.md) でフォントをモードとして完全に分けた結果、ストックとフォントがアプリの中で共有しているものはほとんど無くなった。

| | 今の状態 |
|---|---|
| 一覧に出るもの | ストックにフォントは出さない。フォントモードにはフォントだけ |
| フォルダ・タグ・スマートフォルダ | モードごとに別々（`mode` 列） |
| お気に入り・ピン留め・ゴミ箱・シェルフ | モードの中だけで数える。シェルフの役目も違う（ストックは書き出し・まとめて出力、フォントは比較） |
| 画面 | 一覧・見本・比較・この端末のフォント（[FONT_UI.md](FONT_UI.md)、[SYSTEM_FONTS.md](SYSTEM_FONTS.md)）はフォントだけのもの |
| 共有しているもの | ライブラリのファイル（`library.db`）と、アプリの外側（ウィンドウ、設定、取り込み・書き出し・ライブラリ間のコピー、更新） |

中身はもう別々で、入れ物だけが同じという状態になっている。使う場面も違う（画像・ファイルは「探して使う」、フォントは「比べて選ぶ」。[ARCHITECTURE.md](ARCHITECTURE.md)）。
この端末のフォントの一覧も、もともと別のアプリ（font-preview）で見ていたものを取り込んだ機能だった。

1 つのアプリにまとめておくことで払っているもの：

- ストックの画面にモードの切り替えがあり、モードごとにレイアウト・グループ分け・シェルフの操作が変わる（`MODE_LAYOUTS` / `MODE_GROUPS`、`listKinds`、`modeOf`）。[UI.md](UI.md) の「切り替えで操作の位置を不必要に変えない」を守るための手間がここにかかる
- DB にもモードの区別がある（`folders` / `tags` / `smart_folders` の `mode` 列、`mode_where`、移行の `split_modes`）
- フォントの機能を足すとき、ストックの画面・メニュー・コマンドとぶつからないかを毎回確かめる

## 前に見送ったときの懸念

以前は「分けるとエコシステムが二重になる」として見送り、[ARCHITECTURE.md](ARCHITECTURE.md) に「別アプリに切り出す案は保留中」とだけ残していた。
そこで想定していた分け方は「`features/fonts/` と `src-tauri/src/fonts/` を持ち出し、core をパッケージとして共有する」で、二重になるのは次のものだった。

- コード（core のパッケージ化と、2 つのリポジトリでの版合わせ）
- 配布（ビルド、署名、アプリ内アップデート、リリース）

その後、社内版（jazmf-dx/stockroom）で「同じコードを、設定ファイルと環境変数を変えて別の製品として出す」形（[LIMITS.md](LIMITS.md)）ができた。これを使えば、コードは 1 本のまま分けられる。

## 方針

1. **フォントは Stockroom の中のモードではなく、別のアプリにする。** 最後は、Stockroom はストック（画像・ファイル・テキスト・動画・ブックマーク）、フォントのアプリはフォントだけを扱う
2. **コードは分けない。** このリポジトリから 2 つのアプリをビルドする。フォントのアプリは「機能を絞ったビルド」と同じ形で作る（`STOCKROOM_KINDS=font` と、重ねる設定ファイル）。core のパッケージ化はしない
3. **今のライブラリの中身は失わない。** フォントと画像が混ざったライブラリも、どちらの中身もどちらかのアプリで今どおり使える道を用意する
4. **一度に切り替えない。** 先にフォントのアプリを出し、使えることを確かめてから、Stockroom からフォントを外す

二重になるのは配布（設定ファイル、ビルド、署名の鍵、更新の配信先、リリース）だけにする。社内版でやっていることと同じ量。

## 詰めること

### 名前と ID（人が決める）

[CLAUDE.md](../CLAUDE.md) の「変えないもの」に当たるので、人が決める。

- 製品名（`productName`）と `identifier`。ID が違うと、設定・最近使ったライブラリ・ログなどアプリのフォルダも別になる
- アプリ内アップデートの公開鍵（`pubkey`）と配信先（`endpoints`）。Stockroom と同じ鍵・同じリリースにするか、別にするか。同じ配信先だと、フォントのアプリに Stockroom の更新が入ってしまうので、少なくとも配信先は分ける
- アイコン

### ライブラリの扱い

いちばん重い論点。

- フォントのアプリは、今のライブラリをそのまま開くのか、フォント用の新しいライブラリを作るのか
- 混ざったライブラリから、フォントだけを別のライブラリへ移す手段を用意するか（今の「別のライブラリへコピー・移動」で足りるか、まとめて移す操作が要るか）
- Stockroom からフォントを外したあと、ライブラリに残っているフォントをどう扱うか（隠すだけで残す、開いたときに移すよう促す、など）
- 2 つのアプリで同じライブラリを同時に開いたときのこと。ライブラリのロック（`library.lock`）は、アプリの設定にある端末の ID とプロセスで持ち主を見分ける（`library.rs` の `other_holder`）。ID の違うアプリは設定が別なので、同じ PC でも「別の PC で開いている」と見える
- DB の移行。2 つのアプリが同じ `library.db` を開くなら、版が違うときの移行の順番を考える

### 機能を絞ったビルドで足りるか

- `STOCKROOM_KINDS=font` で、ストックのモードと切り替えが消えるか（種類が 1 つなら設定の「種類」のページは出ない。[LIMITS.md](LIMITS.md)）。実際にビルドして確かめる
- Stockroom 側でフォントを外すには、今は `STOCKROOM_KINDS` に残りの種類をすべて並べることになる。種類を足すたびに直すことになるので、「この種類を除く」の指定が要るか
- フォントのアプリに要らないものを外せるか：ブラウザ拡張・Claude（`STOCKROOM_NO_CONNECT`）、フォルダの共有、まとめて出力、重複の候補など
- メニュー・設定画面・ウィンドウの題名に「Stockroom」と出ているところ（`STOCKROOM_NAME` は版の表示だけ）

### それぞれのアプリに残すもの

- ブラウザ拡張・Claude との連携：フォントのアプリにも要るか。両方で使うなら待ち受けのポートが 2 つになる
- この端末のフォント：フォントのアプリへ。Stockroom からは消える
- 書き出し（[EXPORT.md](EXPORT.md)）・ライブラリ間のコピー・フォルダの共有：フォントのアプリでも使うか

### 配布

- ビルドのワークフロー：今の `build.yml` に足すか、別のワークフローにするか
- 版の番号：2 つのアプリで揃えるか、別々に上げるか。リリースのタグ（`STOCKROOM_TAG_PREFIX`）
- 対応する OS（macOS・Windows の両方か）

### 片付け（Stockroom からフォントを外したあと）

- モードの仕組み（`mode` 列、`modeOf`、`MODES`、モードごとのレイアウト・グループ分け・シェルフ）を残すか消すか。ライブラリをどちらのアプリで開いても読めるうちは、DB の列は消さない
- 将来ストックの中にまた別のモードを作る可能性があるか（あれば仕組みは残す）

### 社内版

社内版（jazmf-dx/stockroom の `docs/CORP.md`）はもともとフォントを外しているので、影響は小さい見込み。Stockroom 側の環境変数の指定を変えたときに、社内版の `corp.yml` を直す必要があるかだけ確かめる。

## 進め方（案）

1. 上の「詰めること」を決め、この文書に書く
2. フォントのアプリのビルドを作る（設定ファイル、環境変数、足りない「外せる仕組み」を [LIMITS.md](LIMITS.md) の形で足す）
3. フォントのアプリを配り、自分で使って確かめる。この間、Stockroom にもフォントのモードを残しておく
4. フォントを別のライブラリへ移す手段を用意する
5. Stockroom からフォントを外す
6. 片付け
