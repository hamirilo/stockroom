# 書き出し：ライブラリ全体を、フォルダ構成どおりに

ライブラリの中は `images/<id>/<元のファイル名>` で、アプリで付けた名前もフォルダ分けもディスクには表れない。
アプリの中では困らないが、ファイルをまとめて持ち出したいときに、そのままでは中身が分からない。

保存の形は今のまま（取り込むときにコピーし、`<id>` のフォルダに置く）にして、**ライブラリ全体の書き出し** で、
その時点のすべてのファイルをアプリのフォルダ構成どおりにコピーできるようにする。1 回コピーするだけで、バックアップとは別のもの。

## 決めたこと

| 論点 | 決定 |
|---|---|
| 保存の形 | 変えない。フォルダ構成どおりに保存する案と、元の場所のまま参照する案は採らない（下の「採らなかった案」） |
| 入口 | メニュー「ファイル」の「書き出し…」の次に「ライブラリ全体を書き出し…」 |
| 書き出し先の構成 | `<ライブラリ名>/<フォルダ>/…/<名前>.<拡張子>`。未分類は `<ライブラリ名>/` の直下。フォントがあった版では間に `<モード>/` があった（[FONT_APP.md](FONT_APP.md)） |
| 対象 | ゴミ箱以外のすべての項目（フォントがあった版のライブラリに残るフォントは除く） |
| 書き方 | 毎回、新しいフォルダにすべてコピーする。前回の書き出しとの比較・上書き・片付けはしない |
| バックアップ | 別のもの。これまでどおり `.library` フォルダのコピー（docs/FEATURES.md「バックアップ」）。書き出したものからライブラリには戻せない |

## 書き出し先の構成

```
書き出し先/
  MyPictures/                      ← ライブラリ名。すでにあれば「MyPictures (2)」
    旅行/2025/京都/金閣寺.jpg
    旅行/2025/京都/金閣寺 (2).jpg
    請求書.pdf                      ← 未分類はライブラリ名のフォルダの直下
```

- **項目が入るフォルダは 1 つ**（`item_folders` の `idx_item_folders_item`、`db.rs` の移行 step 5）なので、書き出す場所も 1 つに決まる。タグはフォルダにしない
- ファイル名はアプリでの名前（`item.name`）に拡張子を付けたもの。使えない文字の置き換え・同じ名前の連番は今の書き出しと同じ（`export_target` / `safe_name`）
- フォルダ名も同じく置き換える（`/` を含む名前も 1 つのフォルダのまま。末尾の点・空白は除き、空・`.`・`..` は `_`。`safe_part`）。同じ親の下に同じ名前のフォルダが 2 つあると、ディスクでは 1 つにまとまる（中の同じ名前のファイルには連番が付く）
- `<ライブラリ名>/` は毎回新しく作る。すでにあれば `<ライブラリ名> (2)/` のように番号を付け、前の書き出しには触らない

## ダイアログ

今の書き出しダイアログ（`ExportDialog.tsx`）に、`ListSource` の `{ kind: "library" }` を足して使う。

```
ライブラリ全体を書き出し
  対象：1,234 件。ファイルはそのままの形式でコピーします

  書き出し先：[ ~/Desktop ]  [選ぶ…]
    「MyPictures」フォルダを作り、フォルダ構成どおりに書き出します
                                            [キャンセル] [書き出し]
```

- フォルダの書き出しにある「サブフォルダを含める」「フォルダ構成を保つ」は出さない（常に全体を、構成どおりに）
- 書き出しはダイアログを閉じてから進む。進み具合は右下のカード（取り込み・別のライブラリへのコピーと同じ）に出し、カードの「キャンセル」で止められる（数 GB になりうる）。
  止めたら、そこまでに書いたものは残す
- 終わったら今の書き出しと同じく「N 件を書き出しました」と「書き出し先を表示」。コピーできなかったファイルは飛ばして続け、件数と名前を添える

## 実装

- Rust：`src-tauri/src/export.rs` を作り、`commands.rs` の `export_items`・`export_dir`・`safe_name`・`export_target` を移す。
  ライブラリ全体の書き出しは Rust 側で DB からフォルダの場所を組み立てる（フロントから `subdirs` を渡さない）
- 書き出す計画（項目ごとの書き出し先）を作る関数と、実際にコピーする関数を分け、計画の方をテストする（未分類・入れ子・同じ名前・使えない文字・ゴミ箱を除く）
- コマンドはコマンド表（`commands.ts`）に `library.export` を足し、メニュー（docs/MENUS.md）から呼ぶ
- `api.ts` のラッパとモック（`src/dev/mockBackend.ts`）を同じ PR で足す

### 実装の順番

1. ~~ライブラリの中のファイルの場所を `library.rs` にまとめる~~（済み。`item_dir` / `stored_file` / `store_file` / `remove_item_dir`）
2. ~~`export.rs` への移動と、ライブラリ全体の書き出し~~（済み。`export_library` / `cancel_export`、`plan` と `write` をテスト）

## 入れないもの

- 前回の書き出しとの差分（変わったものだけ書く・移動を反映する・無くなったものを片付ける）：書き出しは 1 回のコピーで、繰り返し同じ場所を更新する使い方はバックアップの役目
- タグ・評価・メモの一覧（CSV など）：必要になったら足す

## 採らなかった案

- **フォルダ構成どおりに保存する**（`<ライブラリ>/旅行/金閣寺.jpg`）：アプリでフォルダの名前を変える・移す・消す・取り消すたびにディスクの大量の移動になり、
  途中の失敗や同期サービスとの相性が悪い。ディスクで見られると Finder で動かしたくなり、DB とずれる。Windows で使えない文字、大文字と小文字だけ違う名前、
  同じ名前のフォルダ・ファイルの扱いも要る
- **元の場所のまま参照する**（ファイルはコピーせず、タグなどだけを重ねる）：「フォルダごとコピーすれば完結する」前提が崩れ、
  移動・削除・外での書き換えへの追従（再スキャン、ハッシュでのつなぎ直し、見つからない表示、監視）と、asset protocol の許可範囲の拡大が要る。
  Finder でファイルを管理したい使い方になったら考え直す
